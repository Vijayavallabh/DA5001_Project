# Pre-registration: every committed chained arm, re-run with the left-pad slicing fixed (feat-215)

**feat-215.** Committed **2026-09-26**, after a smoke of both queues' code paths (`output/chainfix_smoke`: the 8B
memoriser at `k = 3`, `L = 20` on 4 passages, GPU 4; the 70B `hp1_B` setting at `k = 3` on 2 passages, GPUs 1+2; both
exit 0, protocol lines matching the originals) and before any token of the arms below. Nothing above `## Scoring log` is edited
after the first token.

## Why

`analysis/composition_attack.py` `Attacker.query` sliced each LEFT-padded row at its own token count until
2026-09-26 (caution (bc)), so a row with `p` pad tokens recorded its last `p` prompt tokens as the start of its
generation and counted them in its length. Single-query and oracle-window batches never pad on any committed corpus
or tokenizer (every seed and oracle prompt re-encodes to the length it was cut at), but a chained prompt is the seed
plus the model's own text so far, whose lengths differ, so chained batches do pad. Every committed chained row
(15 CSVs; none cited by the live manuscript) was computed with the defect. The fix (commit to follow this file) is
pinned by `tests/test_composition_left_pad.py`. The user asked for the chained arms to be re-run with it.

## How the results are put back

`analysis/chained_fix.py merge` builds `output/chainfix/merged/<run>`: the old run's per-passage, summary and query
files with every chained row replaced by the re-run's and every other row byte-identical. The committed copies
(`composition_8b_{kl,pathwise}{,_per_passage}`, `composition_comma7b{,_summary}`, `composition{,_summary}`) are
replaced by the merged files; `bank_cap.csv` and `prefix_debt_ablation.csv` have their chained rows spliced from the
merged summaries; `composition_70b.csv`, `odometer{,_per_passage}.csv` and `separation{,_summary}.csv` are
regenerated by their own scripts from the merged inputs.

## Gates

- **G0 (integrity).** Every re-run finishes with `0` queries over budget (`Z > max(0, B) + 1e-3`, and `R` under the
  pathwise constraint); every chained key of the old file (`k`, `L`, passage) is present in the re-run and nothing
  else is.
- **G1 (non-chained rows untouched).** After the merge and the regenerations, every committed row whose mode is not
  `chained` is byte-identical to its committed version. A difference is a defect in the merge, and nothing is
  committed until it is repaired.
- **R0 (reproduction, diagnostic).** A chained arm's first window prompts with the seed alone, which never pads, so
  on the same hardware with the same seed the re-run must reproduce the old window-0 texts exactly. Read on every
  run that kept a query log. If fewer than `95%` match, the environment has drifted since the original, the old and
  new chained numbers differ for more than the fix, and every comparison below says so; the re-run's numbers still
  replace the old ones, since they are the fixed pipeline's.

## Predictions

The mechanism: with the defect a lagging row's recorded window began with a copy of its own previous tail, so the
stitched text carried duplicates. The next prompt still ended where the true text did, so the continuation was not
derailed, but `nv_recall` merges matched blocks only across gaps of at most `2` words and keeps spans of at least
`20` words, so a duplicate longer than two words splits the span there, and a `20`-token window (about `15` words)
then counts for nothing.

- **P1 (direction).** The fix does not lower chained recall: at every (run, `k`, `L`) of the runs with at least
  `50` passages, fixed mean `nv_recall` is at least the defective mean minus `0.02`.
- **P2 (where).** Summed over `k` within each such run, the rise at `L = 20` exceeds the rise at `L = 50`.

The 8-passage *1984* runs are descriptive only. Nothing in the live manuscript cites a chained number; if a
regenerated file moves any number the manuscript does quote, that is a G1 failure.
