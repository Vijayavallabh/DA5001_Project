# Pre-registration: what a selection server actually pays for its draws (feat-164)

Committed **before any anchor-only cell is run**. Nothing above the `## Scoring log` line is edited
afterwards.

## Why this arm exists, and what it corrects

feat-162 measured selection's draws with `h1.py --k-values 0.0` and found one draw costs what one
metered decode costs, `6.99`s against `6.97`s at width `40`. It explained that by saying neither
path is weight-bound at that width. **That explanation is wrong, and the code says so.**
`a_patch/factory.py` forwards **both** models at **every** step:

```
safe_logits,  safe_past  = self.forward_direct(self.safe_model,  ...)
risky_logits, risky_past = self.forward_direct(self.risky_model, ...)
```

and the `k_radius == 0.0` branch below it consumes `risky_logits` only to build a zero budget. So
the "anchor draws" path runs the `8.03`B risky model on every token and throws the result away.
The two paths measure the same because **they are doing the same work**, not because the extra
model is free. feat-163 then measured the consequence without knowing it: the ratio stays flat out
to width `200`, which is what identical work looks like.

This matters beyond the explanation. `output/phase5/sel_anchor64` --- the committed selection arm
the paper's headline rests on --- was generated by that same path, so **every serving number this
project has published prices a research harness that runs two models where a deployment runs one.**
`35.4x`, `67.2x`, `4.11x` and `1.07x` are all upper bounds on what a selection server pays.

A harness that forwards both models is the right design for an audit: it is how a budgeted decoder
is compared against its own anchor step by step, and every *decoding* number in this paper depends
on it. It is the wrong thing to time.

## What runs

Host B, one H100, box otherwise idle, at widths **`64` and `200`**, `--max-new-tokens 200`, the
same neutral prompts, each cell twice, loader separated from work by running one **and** two
completions exactly as feat-162 and feat-163 did.

**Cells `A` and `D` are not re-run: they are feat-163's `ANCHOR` and `MET` cells at those two
widths**, measured on this host, on this card, within the hour, under a gate (feat-163's G0) that
pins them to feat-162. Re-running them would add a cross-arm comparison where a within-arm one is
available. Only `B` and `C` are new, which is why the compute below is twenty minutes and not an
hour.

| cell | what it isolates |
|---|---|
| `A` harness, anchor + Llama-3.1-8B (`--k-values 0.0`) | what every published draw cost is |
| `B` harness, anchor + anchor (`--safe-model-path`=`--risky-model-path`) | our loop, both forwards small |
| `C` plain `generate()`, anchor alone | what a selection server runs |
| `D` harness, metered `k=10` | the comparison arm, unchanged |

`A - B` is the cost of carrying the `8.03`B model; `B - C` is what our loop costs over a plain one
at the same model size and is **not** attributable to either mechanism; `C` is the draw cost a
deployer pays.

## Gates

- **G0 (instrument).** Cell `A` at width `64`, inherited from feat-163, must have passed that
  arm's own G0 --- within `25%` of feat-162's `6.99`s per completion. If feat-163's G0 failed,
  this arm has no `A` to subtract and nothing below is read.
- **G0b (the self-paired cell is the same loop).** Cell `B` must serve the same requests and the
  same mean tokens as cell `A` at the same width. `B` differs from `A` in one argument, the risky
  model's path; if anything else moved, the subtraction `A - B` is not the cost of the `8.03`B
  model.
- **G1 (same work served).** All four cells must serve the same number of requests at a width and
  their mean served tokens per request must agree within `10%`. Cell `C` is a different decoder
  loop, so this is the check that it is nonetheless generating the same amount of text.

## Bands, committed before the data

- **B1 -- what fraction of the published draw cost is the discarded model?** `(A - B) / A` at
  width `200`, where weights should matter most. **DOMINANT** if `> 0.50`, **SUBSTANTIAL** if `0.20`--`0.50`, **MINOR** if `< 0.20`.
- **B2 -- the deployable draw cost.** `C / A` at width `200`, the factor by which every published
  selection serving number overstates a deployment.
- **B3 -- the compute-matched cell, re-derived.** Using `C` for the draws and `D` for the meter,
  both at width `200`, the matched `n` is `argmin |n C/D - 1|`, and the judged gain at that cell is
  read from `results/compute_matched.csv` exactly as feat-162 read it. Reported whatever it says,
  including if it lands on the `n=4` cell the paper originally claimed --- **which would mean the
  manuscript's `0.92x` was right for the wrong reason and feat-162's B2 must be restated.**

## What we predict

The `8.03`B model is `4.6x` the anchor's parameters, so at width `200`, where weights should
matter, we predict B1 **DOMINANT** at `0.6`--`0.8` and B2 at `0.2`--`0.4`. That would put the
matched cell near `n=3`--`5` and make the paper's original `n=4` cell close to correct.

## Excluded in advance

- Revising any *decoding* result. This arm times a code path; it does not re-decode anything, and
  no judged, leakage or budget number in this paper depends on how fast the harness runs.
- Using cell `C` to claim a price for the metered decoder. A metered decoder needs both models by
  definition; only selection's draws do not.
- Quoting `B - C` as anyone's cost. It is our loop's overhead and belongs to neither mechanism.
- Reading any band if G0 fails.

Both gates pass. `C` served `64` and `200` sequences of exactly `200` new tokens.

- **B1: SUBSTANTIAL**, `(A-B)/A = 0.3367` at `W=200`. We predicted DOMINANT at `0.6`--`0.8` and

  two-thirds, because at `4.6x` the parameters the `8.03`B forward costs only `1.88x` the anchor's
  --- `8.375`s against `4.463`s --- so the regime is only partly weight-bound even at width `200`.
- **B2: `C/A = 0.3476`.** **Every selection serving number this project has published overstates a
  deployment by `2.88x`.**
- **B3: the matched cell is `n=2` at `0.68x`**, and its paired judged difference against the
  metered decoder is **`-0.0330` `[-0.0625, -0.0025]`**, which excludes zero. **CONCESSION
  STANDS.**

### What the three cells decompose into, which is cleaner than B1 alone

`B = 8.515` against `2C = 8.926`: **our loop with two small models costs slightly less than two
plain generates**, so the harness's own overhead is not measurable here and every gap between these
cells is a model forward. That makes the split exact: at `W=200` the anchor forward is `4.463`s and
the `8.03`B forward is `A - C = 8.375`s. B1's registered quantity compares `A` against `B`, which
still contains a second small forward a deployment would not run either, so **B1 understates what a
deployment saves and B2 is the number to quote**: a selection server runs one model where the
harness runs two, and pays `35%`.

### What this does and does not revise

**It does not revise a single decoded, judged, leakage or budget number.** The harness forwarding
both models is the right design for an audit --- it is how a budgeted decoder is compared against
its own anchor step by step --- and nothing about what was generated or scored depends on how fast
it ran. What it revises is every wall-clock number, all of which are now upper bounds:

| quantity | as published | what a deployment pays |
|---|---|---|
| selection `n=64` vs metered, per request | `67.2x` (feat-162, host B) | `64 x C/D = 21.8x` |
| selection `n=64` vs metered, ratio of totals | `35.4x` (local A100) | not measured on that host |
| compute-matched cell | `n=4` at `0.92x` (FLOP proxy) | **`n=2` at `0.68x`** |

And it revises, for the second time in one evening, the *explanation* of why the measured ratio
sits where it does. feat-162 wrote into the manuscript that one anchor draw costs what one metered
decode costs "because at batch `40` neither path is weight-bound". **That sentence is wrong and is
withdrawn**: they cost the same because the draw path runs the same two models the metered path
runs. The mechanism was there to be read in `a_patch/factory.py` and we timed around it instead.
Caution (ay) is amended accordingly, and the lesson it now carries is the one this arm is about:
**before timing two code paths against each other, read what each one runs.**

### Three things not claimed

`C` is a plain `generate()`, so it is a *different decoder loop* from `A`, `B` and `D`. What
licenses comparing it is that `B ~ 2C` --- the harness loop is not slower than a plain one at the
same work --- and that is measured here rather than assumed. The metered decoder needs both models
by definition, so `D` is already close to deployable and no `C`-style cell was run for it. And B3
prices draws only: adding the `0.494`B reward pass at `n=2` (`0.543`s, feat-162) moves `0.68x` to
`0.72x` and does not change which cell is the argmin.
